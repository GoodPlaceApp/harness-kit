# `refl.pack-retro` — When is this way of working itself reviewed?

```yaml
slot: refl.pack-retro
title: The process is revisited on a trigger, not a calendar
statement: >
  The way of working is reviewed when something happens that should change it: an incident,
  a rule that was broken twice, a practice that has been skipped repeatedly, a tool that
  changed, or a stated risk whose acceptance expired. Each review asks one question — which
  rule would have prevented this, or which rule is costing more than it returns — and its
  output is an amendment to the standing rules, not a discussion.
rationale: >
  A calendar retrospective with one participant becomes a formality quickly. Trigger-driven
  review keeps the connection between a real event and a rule change, which is the only form
  of process change that survives. A rule repeatedly skipped is data about the rule, not
  about the operator.
tier: U
evidence: documented
corroboration: 2
check: null
```

**Adapted for one person.** The team retrospective collapses into post-incident rule-writing
plus a standing habit of noticing skipped rules. What is lost is the outside perspective;
the substitute is an agent asked to review the rules adversarially against recent history —
which rules were followed, which were not, and which never applied.

**Sources** — Google SRE Workbook on postmortem-driven process change; DORA's generative
culture findings on learning from failure as a delivery capability.
